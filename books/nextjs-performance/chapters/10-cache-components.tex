\paragraph{무엇.}
U4는 route를 static shell과 Suspense 구멍으로 나눈다. 데이터 읽기는 모두 구멍 안으로 옮긴다.
\code{proxy.ts}는 없는 page를 렌더 전에 진짜 HTTP 404로 보낸다.
오너 제약이 있다. 모르는 page는 진짜 404여야 한다(\decision{89}).
% src: cc.design.md §1, §7.1; decisions.plan.md #89, #97

\paragraph{왜.}
동적 route는 page payload를 prefetch하지 못하고 클릭마다 왕복이 생긴다(감사 A1, A4, A5).
static shell을 prefetch하고 cache하면 이 왕복이 줄 것으로 기대했다.
% src: perf.audit.md §0 S1, §2 A5; cc.design.md §1

\paragraph{어떻게.}
\begin{enumerate}[nosep]
  \item flag를 켜면 route는 static shell과 구멍으로 나뉜다. 요청 시점 API(\code{cookies()}, \code{auth()})는 Suspense 안에서만 읽는다.
  \item 새 param 경로의 첫 요청에서 Next가 shell을 runtime prerender로 만든다. 캐시되지 않은 fetch는 그동안 걸려 있다가 reject된다.
  \item 우리 \code{catch}가 이 reject를 오류로 삼키지 않도록 \code{unstable_rethrow}를 넣었다(\Cref{sec:le-prerender}).
  \item proxy는 없는 user, project, post를 API로 확인해 404로 보낸다. 시도 1에서는 알 수 없는 최상위 경로가 500이었고 A2 수정으로 고쳤다(\Cref{sec:re-u4-a1}).
\end{enumerate}
% src: u4o-prerender-errors.md "원인", "처방"; cc.report.md MVP2; decisions.plan.md #97

\paragraph{언제 효과가 있나, 없나.}
\begin{itemize}[nosep]
  \item 익명 이동은 엣지 HIT라 오리진 변화가 안 보인다. 시도 2에서 익명 합은 218에서 201 ms였다.
  \item 로그인 이동은 \cfs{DYNAMIC}이라 매번 오리진에 간다. 로그인 s4, s5에서 시도 2는 +34, +95 ms였다.
  \item 이 이동 시간 비교는 흔들림과 섞여 판정이 없다(\Cref{sec:re-u4-aba}). 시도 2의 329 $\to$ 434 ms는 같은 코드 경로가 10:17에 476 ms였던 것(\decision{102} Update)과 섞였다. 회귀의 근거가 아니다.
  \item 시도 2는 메뉴 링크당 prefetch가 2에서 6, 로그인 10초 요청이 53 / 50 / 50이어서 G-a, G-b를 깼다.
\end{itemize}
% src: u4-verdict.md §2.3, §3; u4-aba-verdict.md §0

\paragraph{왜 중요한가.}
이 단위가 G-CC의 판정 단위였다. 주 지표 판정이 없어 G-CC는 미달로 닫혔다(\decision{105}, \decision{111}).
U5와 U6은 flag가 켜져 있어야 돈다(\decision{102}).

\subsection{P2 gate 발견: \texttt{/@u/logs/<id>}가 soft 404였다}\label{sec:cc3-p2gate}

\paragraph{결과.}
P2 gate 1회차(cycle 1)는 ISSUE였다. 운영의 \code{/@taeklim/logs/0}, \code{/abc}, \code{/99999999999999}, \code{/@nobodyxyz/logs/31}이 not-found 화면을 HTTP 200으로 냈다. 2회째 요청은 \cfs{HIT}, \code{age} 90이었다.
\code{df0a482}로 고친 뒤 2회차(cycle 2)는 PASS였다. 네 경로 모두 2회 다 404 \cfs{BYPASS}였고 \code{/@taeklim/logs/31}은 200으로 남았다.
% src: p2-gate.review.md cycle 1 M-1, cycle 2 C2; decisions.plan.md #115

\paragraph{왜.}
gate의 \code{classifyGatePath}가 3세그먼트 경로를 \code{projects}일 때만 분류했다. \code{/@u/logs/<id>}는 \code{null}이라 존재 검사를 받지 않았다.
그러면 \code{cacheComponents} 아래서 \code{loading.tsx}의 shell이 먼저 흘러간다. page 안의 \code{notFound()}는 그 뒤 스트림에서 실행된다. 이때 상태 줄은 이미 200이다.
% src: p2-gate.review.md cycle 1 M-1 "원인 (코드)"

\paragraph{무엇.}
gate 종류 \code{log}를 더했다(\decision{115}). 하지 않은 일도 정했다.
\code{loading.tsx}를 빼거나 \code{export const dynamic}을 되돌리지 않았다. 빌드가 깨지고(\decision{97}) PJ-2-03 AC3이 금지한다.
% src: decisions.plan.md #115; p2-gate.review.md cycle 1 M-1 "피할 안"

\paragraph{어떻게.}
\begin{enumerate}[nosep]
  \item 경로가 \code{/@u/logs/<id>} 모양이면 종류를 \code{log}로 분류한다.
  \item \code{<id>}가 1에서 9로 시작하는 숫자 1개에서 19개가 아니면 네트워크 없이 없는 것으로 본다.
  \item 맞으면 \code{GET /v1/api/log/thread/<id>?limit=1}을 부르고 글쓴이를 handle과 비교한다.
  \item API가 404면 맞는 route가 없는 경로로 rewrite해 진짜 404를 낸다. 삭제된 log는 tombstone 화면을 보이므로 있는 것으로 본다. 그 밖의 오류와 시간 초과는 통과시킨다(fail-open).
\end{enumerate}
예: \code{/@taeklim/logs/abc}는 숫자가 아니므로 API를 부르지 않고 404다. \code{/@taeklim/logs/31}은 있는 log라 200이다.
% src: p2-gate.review.md cycle 2 C2 "코드 (df0a482)"; apis/existence.proxy.ts checkLog; utils/notFoundGate.ts isLogId

\paragraph{언제 효과가 있나.}
\begin{itemize}[nosep]
  \item gate는 경로 모양이 gate 종류에 들어올 때만 돈다. 동적 route를 새로 만들고 종류를 더하지 않으면 같은 soft 404가 다시 난다.
  \item API 오류와 시간 초과는 통과시키므로(fail-open) 그 순간에는 gate가 404를 보장하지 않는다.
  \item 배포 때 엣지에도 같은 일이 있었다. PM2 reload 중에 엣지에 200이 하나 남았고 두 번째 purge로 지웠다.
\end{itemize}
% src: p2-gate.review.md cycle 1 M-1 "원인 (코드)"; apis/existence.proxy.ts; 01.status.md 2026-10-14 pj "재purge 1회 (reload 중 엣지에 남은 200)"

\paragraph{왜 중요한가.}
soft 404는 Cloudflare에 하루 남는다. 오너 선 ``모르는 page는 진짜 HTTP 404''(\decision{89})가 운영에서 깨진다.
AC가 전부 PASS여도 이 선이 위라서 gate는 ISSUE였다.
% src: p2-gate.review.md cycle 1 M-1 "깨진 선", 판정

\section{U5: 공개 읽기에 \texttt{'use cache'}}\label{sec:cc3-u5}

\paragraph{무엇을 알려고 쓰나.}
자주 바뀌지 않는 공개 읽기 3개를 Next 안쪽에 캐시하면 MISS 렌더의 첫 바이트(TTFB)가 빨라지는가.

  \centering\small
  \begin{tabularx}{\linewidth}{@{}L{3.0cm} L{3.0cm} Y@{}}

글 본문과 피드는 넣지 않았다. 변경이 잦고 비공개 글 token 경로가 섞이기 때문이다.
% src: cc.design.md §7 note "글 본문과 피드는 U5에 넣지 않는다"

\paragraph{무엇.}
세 fetcher에 \code{'use cache'}와 \code{cacheTag}, \code{cacheLife('hours')}를 붙였다.
\code{'use cache'} 안에서는 \code{cookies()}와 \code{headers()}를 쓸 수 없다. 기본 저장소는 메모리 LRU다.
그래서 token이 있는 호출은 언제나 캐시 밖 잎이다. 비공개 글이 캐시에 들어갈 길이 없다.
% src: cc.design.md §2 table (use-cache.md), §7.2 note

\paragraph{왜.}
지금은 MISS 렌더마다 태그, tree, 목록을 \code{blog-api.}에서 다시 읽는다.
이 읽기는 요청마다 다시 나가는 no-store 읽기였다. U0b 기준 MISS TTFB는 280 / 263 / 210 ms였다(중앙값 263).
% src: cc.design.md §1 table (Next 데이터 캐시 = 없음); criteria.md §1 U5 row

\paragraph{어떻게.}
\begin{enumerate}[nosep]
  \item 요청이 Next까지 와서 이 읽기를 부른다.
  \item Next가 \code{cacheTag}로 묶은 안쪽 캐시를 먼저 본다. 있으면 \code{blog-api.}를 부르지 않는다.
  \item 없으면 지금처럼 읽고 그 결과를 \code{cacheLife('hours')} 동안 둔다.
\end{enumerate}

\paragraph{왜(설계의 순서).}
순서가 중요했다. purge를 먼저 하면 엣지가 옛 Next 캐시로 다시 찬다.
\code{expire: 0}이 아니라 \code{'max'}(stale-while-revalidate)면 첫 요청이 옛 값을 내고 엣지가 그것을 1일 저장한다.
\begin{enumerate}[nosep]
  \item 글 발행 또는 수정이 DB에 쓰인다.
  \item (1) \code{my.}의 revalidate route가 tag를 만료시킨다.
  \item (2) \code{cf-purge.sh}가 엣지를 비운다.
\end{enumerate}
% src: cc.design.md §8.3

\paragraph{왜 뺐나.}
오너 답은 이렇다. 실시간으로 갱신할 필요가 없고 1일은 기다릴 수 있다. 필요하면 Cloudflare 캐시를 무효화한다.
비밀 키를 받는 POST 끝점이 하나 느는 것도 이유다(KISS).
branch \code{cc-u5}에서 \code{/api/revalidate}, \code{cf-purge.sh} 호출, \code{updateTag}를 되돌렸다.
handler는 \code{app/api/x_revalidate/x_route.ts}로 보관한다. route가 아니다.
% src: decisions.plan.md #109

\paragraph{남는 지연과 대처.}
\begin{itemize}[nosep]
  \item purge 뒤에도 Next 안쪽 캐시(\code{cacheLife('hours')})가 tree, projects, tags를 그 수명 동안 옛 값으로 줄 수 있다.
  \item 그 사이 엣지가 다시 저장하면 다음 purge까지 남는다.
  \item 급하면 한 시간 뒤 purge를 한 번 더 한다.
\end{itemize}
% src: decisions.plan.md #109 "남는 지연"

\paragraph{언제 효과가 있나, 없나.}
U6이 없어도 \code{cacheLife}가 최대 지연의 상한이다. 글 본문과 피드는 U5 대상이 아니라 이 지연과 무관하다.
% src: cc.design.md §8.3 note ("잊어도 cacheLife가 최대 지연을 막는다"), §7 note

\paragraph{왜 중요한가.}
M-CC3 exit에서 U6의 정확성 판정 항목이 빠졌다. U6 행은 오너 결정으로 닫았다.
% src: decisions.plan.md #109 Consequences

\paragraph{지금 상태.}
뺌(\decision{109}). 판정은 없다.

\section{캐시 층 지도: 누가 어디서 무엇을 기억하나}\label{sec:cc3-map}

\paragraph{결과.}
React \code{cache()}와 React Query는 같지 않다. 서로를 대신하지 못한다.
\code{cache()}는 서버에서 렌더 하나 동안만 기억한다. React Query는 브라우저에서 탭이 열려 있는 동안 기억한다.

\begin{inbrief}

\paragraph{어떻게.}
글 상세 페이지를 여는 예다.
\begin{enumerate}[nosep]
  \item 독자가 글 상세를 연다. 엣지가 MISS면 요청이 Next 서버까지 온다.
  \item 서버가 렌더한다. layout, \code{generateMetadata}, rail이 \code{getUserProfile}을 여러 번 부른다.
  \item \code{cache()}가 같은 인자의 호출을 하나로 묶는다. Express 호출은 1번이다. 글 상세 MISS 렌더의 서버 fetch는 모두 4개다(U2 이후 기록, \code{cc.report.md}).

  \item 로그인한 독자의 브라우저에서 client component가 \code{useMe}를 부른다. React Query가 값을 받아 키 \code{['users', 'me']}에 둔다.

  \item 같은 링크를 30초 안에 다시 누르면 router cache(\code{staleTimes.dynamic = 30})가 앞의 RSC 결과를 다시 쓴다.
\end{enumerate}
