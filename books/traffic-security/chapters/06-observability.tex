\section{웹 요청 로그 (A)}\label{sec:06-requestlog}

\begin{inbrief}
  \item[Why] 트래픽이 터졌을 때 누가, 어디서, 무엇을 요청하는지 알아야 막을 대상을 고른다.
  \item[When] 페이지 요청이 VM의 Next 서버에 닿을 때마다 한 줄을 쓴다.
  \item[Where] \texttt{apps/dashboard\_client\_web/proxy.ts}에서 쓰고 Cloud Logging에서 읽는다.
  \item[How] JSON 한 줄을 stdout에 쓰고, PM2 로그 파일과 Ops Agent를 거쳐 Cloud Logging에 보낸다.
\end{inbrief}

Cloud Logging에 INFO 줄, path, country가 보인다.

\begin{description}
  \item[왜 필요했나] 트래픽이 터졌을 때 누가, 어디서, 무엇을 요청하는지 알아야 한다. 그래야 막을 대상을 고를 수 있다.
  \item[문제] \texttt{blog-web}은 요청을 기록하지 않았다. \texttt{blog-api}에만 로그가 있었다.
  \item[무엇을 바꿨나] \texttt{proxy.ts}가 페이지 요청마다 JSON 한 줄을 쓴다. 항목은 \Cref{tab:06-log-fields}에 있다.
  \item[어떻게] PM2 로그 파일, Ops Agent, Cloud Logging 순서로 간다. 보관은 Cloud Logging 30일, VM의 PM2 로그 7일(logrotate \texttt{rotate 7})이다. 로컬에서 끄려면 \texttt{LOG\_REQUESTS=false pnpm dev:web}을 쓴다.
  \item[왜 이 방법인가] 미들웨어(proxy.ts)에서 찍으면 모든 페이지 요청을 한 곳에서 잡는다. Ops Agent는 이미 \texttt{blog-api} 로그를 보내고 있어서 같은 길에 하나만 더했다. 전체 IP는 오너 결정이다 (\decision{58}). 공격 IP를 정확히 막으려면 필요하다.
  \item[확인] Cloud Logging에 INFO 줄, path, country가 보인다. 상위 경로 조회가 동작한다.
  \item[한계] Cloudflare \cfs{HIT} 요청은 VM까지 오지 않으므로 이 로그에 없다. 전체 요청 수는 Cloudflare Analytics에서 본다.
\end{description}

\subsection{시각 있는 JSON 오류 줄}\label{sec:06-errorjson}

\paragraph{결과.}
커밋 \commit{35b3630}이 \texttt{blog-web}의 오류 줄에 시각을 넣었다.
커밋하고 push했다.
VM에는 아직 배포하지 않았다.
그래서 JSON 오류 줄을 실제 출력에서 아직 보지 못했다.

\paragraph{무엇을 알려고 하나.}
오류 줄이 옛 것인가 새 것인가.

\paragraph{문제.}
\texttt{pm2 logs blog-web --err}의 오류 줄에 시각이 없었다 (\Cref{sec:dbg-case13}).
옛 줄과 새 줄을 가를 수 없었다.

\paragraph{원인.}
시각 없는 줄은 두 종류였다.
\begin{itemize}[nosep]
  \item \texttt{console.error} 문자열. 예: \texttt{[RecentPostsList] feed fetch failed}.
  \item Next.js가 직접 찍는 여러 줄 출력. 줄 앞에 x 모양 기호가 붙고 \texttt{[TypeError: fetch failed]}와 digest가 나온다. Next 내부라 바꿀 수 없다.
\end{itemize}
JSON 줄은 이미 \code{time}을 가진다.
\texttt{blog-api}의 pino는 \texttt{logger.ts:24}에서 isoTime으로 쓴다.
\texttt{blog-web} 요청 로그는 \texttt{proxy.ts:38}이 쓴다.

\paragraph{처방.}
오너는 먼저 PM2 \code{log_date_format}을 청했다.
채택하지 않았다.
PM2가 모든 줄 앞에 날짜를 붙이기 때문이다. 예: \code{2026-10-13T23:40:01: {"level":30,...}}.
그러면 Ops Agent의 \code{parse_json}이 모든 pino 줄과 요청 JSON 줄에서 실패한다.
Cloud Logging이 구조화 필드, severity 매핑, 요청 로그 질의를 잃는다 (\decision{56}, \decision{58}).
그래서 시각 없는 줄을 JSON으로 바꿨다.
\texttt{ops-agent.yaml}은 그대로다.
\Cref{tab:06-errorjson}가 줄 종류별로 무엇이 바뀌었는지 보인다.

코드 위치는 \texttt{apps/dashboard\_client\_web}다.
\begin{itemize}[nosep]
  \item 새 파일 \texttt{utils/serverLog.util.ts}: \code{toErrorLogLine(severity, message, err?, context?)}(순수 함수)와 \code{logServerError(message, err?, context?, severity='ERROR')}.
  \item \texttt{instrumentation.ts}의 \code{onRequestError}: 먼저 \code{logServerError}를 \code{'request error'}와 키 \code{digest}, \code{path}, \code{method}, \code{routerKind}, \code{routePath}, \code{routeType}로 부르고, 그 뒤 Express \code{/v1/api/error-logs}로 POST한다(원래 있던 동작).
  \item \code{console.error}를 \code{logServerError}로 바꾼 파일은 아래 둘이다.
  \begin{itemize}[nosep]
    \item ERROR(다시 던진다): \code{apis/getPostsByTag.api.ts}, \code{getUserPopularTags.api.ts}, \code{getPosts.api.ts}, \code{getUserProfile.api.ts}, \code{getPopularTags.api.ts}, \code{getPost.api.ts}.
    \item WARNING(대체 경로로 처리): \code{app/sitemap.ts}, \code{app/blog/components/RecentPostsList.server.tsx}.
  \end{itemize}
  \item 클라이언트 컴포넌트는 그대로다. 브라우저에서 로그를 남긴다.
  \begin{itemize}[nosep]
    \item \code{error.tsx} 파일들, \code{CategoryErrorboundary.client.tsx}, \code{useDraftAutosave.hook.ts}.
  \end{itemize}
\end{itemize}

줄의 키는 context 키, \code{time}(ISO), \code{severity}(\code{ERROR} 또는 \code{WARNING}), \code{message}, \code{err}, \code{cause} 순서다. \code{err}와 \code{cause}는 각각 \code{name}, \code{message}, \code{code}를 가진다.
고정 키를 context 뒤에 펼치므로 context가 덮어쓰지 못한다.
\code{LOG_REQUESTS}로 끄지 않는다.
\code{cause.code}가 \code{ETIMEDOUT} 같은 코드를 나른다.
undici가 이를 감싼다: \code{TypeError: fetch failed}의 cause가 \code{AggregateError}이고 코드가 \code{ETIMEDOUT}이다.

아래 줄은 코드에서 추정한 것이다. 아직 관찰하지 않았다.

\paragraph{부작용.}
\begin{itemize}[nosep]

\end{itemize}

\subsection{거짓 MISS와 재시도 수정}\label{sec:06-false-miss}

% src: deploy/traffic/review/04-observability.md §F 왜 이 방법인가; deploy/traffic/README.md §5; _scripts/cloudflare/traffic-check.sh hit_status
\paragraph{결과.}
첫 실행(issue \#4)에서 \cfs{MISS} 2건이 잘못 FAIL이 되었다.
\code{hit_status}가 최대 4번 시도하도록 고친 뒤 issue \#5는 14 PASS, 0 FAIL이다.

\begin{description}
  \item[문제] 한 번 데워 둔(warm) 뒤 두 번째 GET이 \cfs{HIT}여야 한다. GitHub runner에서는 \cfs{MISS}가 나왔다.
  \item[원인] GitHub runner는 연결마다 다른 Cloudflare 캐시 서버로 갈 수 있다.
  \item[처방] \code{hit_status}가 \cfs{HIT}를 최대 4번 시도하고, 시도 사이에 1초 쉰다. 4번 다 \cfs{MISS}일 때만 진짜 실패로 본다.
  \item[근거] 연결이 달라서 생긴 \cfs{MISS}는 다시 시도하면 사라질 수 있다. 4번 모두 \cfs{HIT}가 아니면 규칙 문제로 읽는다.
\end{description}
