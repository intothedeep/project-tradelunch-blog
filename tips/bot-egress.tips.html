Step 1 of 4

1. 문제: 봇 하나가 캐시를 피했다

결론: 봇 하나가 무작위 필터 URL로 캐시를 피했다. 그래서 요청마다 Supabase까지 갔다.

알려는 것: 무료 한도를 넘긴 egress(서비스 밖으로 나가는 데이터 양)를 누가 만들었나.

핵심 흐름: 봇 한 번이 Supabase까지 가는 길

봇 요청 하나가 SSR을 거쳐 API 7번이 되고, 그중 BYPASS 네 갈래가 Supabase까지 간다. 노란 줄이 캐시를 못 쓰는 곳이다. 왜: 캐시가 막지 못하면 요청 하나가 SQL 5~6개가 된다. 출처: history/2026-11-18-alibaba-bot

  • 피드(/users/taeklim)가 매번 MISS인 이유: 봇이 ?categories=…&tags=…를 무작위로 바꾼다. apis/buildFeedQuery.ts가 그 값을 피드 API 주소로 넘긴다.
  • 흐름의 끝: 과부하, SSR fetch timeout, error_log INSERT 순서로 이어진다.

왜 캐시가 안 먹었나
  • 캐시(cache)는 주소가 같을 때만 답을 재사용한다. 봇은 주소를 매번 바꿨다. 그래서 MISS가 났다.
  • SSR이 부르는 API 4곳은 Cache-Control 헤더가 없었다. 그래서 BYPASS가 났다. Cloudflare가 아예 캐시하지 않았다.
  • 4곳: /tags, /users/:u/tags, /users/:u/profile, /users/:u/categories.

2. 확인: 이렇게 찾았다 (다음에도 똑같이 한다)

알려는 것: 느린 쿼리가 아니라 호출 수를 보는 법, 그리고 누가 부르는지 좁히는 순서. 5가지를 위에서 아래로 한다.

a. Supabase: 호출 수(calls)로 정렬한다
  • Supabase 대시보드의 Query Performance 표를 내보낸다. 느린 쿼리가 아니라 calls 열을 본다.
  • 이유: 평균 시간이 짧아도 호출이 수십만 번이면 전송량이 쌓인다.

읽는 법: 느린 쿼리는 없다. 문제는 호출 수다. 카테고리 트리는 본문(p.content)을 공통 테이블 식(common table expression, CTE) 안에서만 읽고 마지막 SELECT에서는 뺀다. 그래서 본문 전송은 원인이 아니다.

b. Cloudflare GraphQL API: curl과 jq로 묻는다

토큰과 존 ID는 환경 변수로 읽는다. 파일에 쓰지 않는다. 아래 값은 자리표시다.

# 하루 단위 요청 수 (httpRequests1dGroups)
curl -s https://api.cloudflare.com/client/v4/graphql \
  -H "Authorization: Bearer $CF_API_TOKEN" -H "Content-Type: application/json" \
  --data '{"query":"{ viewer { zones(filter:{zoneTag:\"'"$CF_ZONE_ID"'\"}) {
    httpRequests1dGroups(limit:40, filter:{date_geq:\"2026-10-15\"}) {
      dimensions { date } sum { requests cachedRequests bytes } } } } }"}' \
  | jq '.data.viewer.zones[0].httpRequests1dGroups[]'

# 호스트, 경로, 캐시 상태별 (httpRequestsAdaptiveGroups)
#   같은 방식으로 묻고 dimensions에 아래 값을 고른다
#   clientRequestHTTPHost  clientRequestPath  cacheStatus  userAgent  clientIP
  • httpRequests1dGroups는 날마다의 요청 수와 캐시된 요청 수를 준다. 그래서 언제 튀었나가 보인다.
  • httpRequestsAdaptiveGroups는 호스트, 경로, 캐시 상태, UA, IP로 쪼갠다. 그래서 누가 무엇을 부르나가 보인다.
  • 무료 플랜의 한계: ASN과 query string은 읽을 수 없다. 그리고 경로별 일별 기록은 보존 기간이 짧아 11-08부터만 있었다.

3. 조치: 막고, 캐시하고, 줄인다

알려는 것: 조치마다 Supabase egress와 GCP VM egress를 어떻게 줄이나. 상태는 2026-11-18 기준이다.

조치가 흐름을 끊는 곳

4. GCP egress 읽는 법과 통과 기준

알려는 것: VM에서 나가는 바이트는 어떤 응답인가. 그래서 어느 조치가 얼마나 도우나.

  • VM에서 나가는 바이트는 Cloudflare가 캐시로 답하지 못한 응답이다.
  • 캐시로 답하면 요청은 VM에 오지 않는다. 그래서 VM이 보내는 바이트가 없다.
  • SSR이 blog-api.를 공개 주소로 부른다. 그래서 API 응답은 터널(tunnel)로 한 번 더 나간다.
  • 봇 페이지 하나는 HTML 응답과 API 응답 여러 개를 VM에서 내보낸다.
순서방법줄어드는 것

2API 4곳 캐시페이지당 API 응답 약 40 KB 중 대부분
3필터 query 정규화 (M 설계)같은 필터의 다른 순서가 같은 캐시를 쓴다
4월 기록 (check.md 11)11월 청구에서 전후를 GB로 본다
추정과 실측을 구분한다
  • Supabase egress 추정: 230,000회 × 약 50 KB ≈ 11 GB.
  • 이 값은 API 응답 크기로 계산한 추정이다. DB 바이트를 잰 값이 아니다.

용어 부록

  • egress: 서비스 밖으로 나가는 데이터 양. 무료 한도를 넘으면 과금된다.
  • 캐시(cache)의 상태 HIT, MISS, BYPASS: Cloudflare가 저장본으로 답하면 HIT, 저장본이 없으면 MISS, 서버가 허락하지 않아 아예 저장하지 않으면 BYPASS.
  • 자율 시스템 번호(autonomous system number, ASN): 인터넷에서 한 회사의 IP 묶음에 붙은 번호.
  • 웹 방화벽(web application firewall, WAF): 요청 조건으로 막거나 시험하는 Cloudflare 규칙.
  • 서버 렌더링(server-side rendering, SSR): Next 서버가 HTML을 만드는 단계.
  • 공통 테이블 식(common table expression, CTE): SQL의 WITH 블록.
